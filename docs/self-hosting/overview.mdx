Run GAIA on your own machine with the GAIA CLI. It scaffolds your environment, starts every service with Docker, and gets you to a working instance in a few commands.

## What runs

- **Web**: Next.js
- **Backend**: FastAPI
- **Databases/Infra**: PostgreSQL, MongoDB, Redis, ChromaDB, RabbitMQ (via Docker)
- **Workspace storage**: JuiceFS (per-user file uploads, agent artifacts, skills)

## Prerequisites

- Node.js 20+ and one package manager (npm, pnpm, or bun)
- Docker Engine 20.10+ and Compose v2+
- 2+ CPU cores, 10GB+ disk, **8GB+ RAM recommended** — the shared embedding sidecar alone measures ~1.9–2.4GB RSS (model floor to peak load), and infra + sidecar together measured ~2.5GB on a running stack; 8GB leaves headroom once `gaia-backend`, `gaia-web`, and `arq_worker` are added (their own footprint wasn't re-measured for this guide — 8GB is the safe floor, not a hard minimum verified down to the last MB)
- `OPENROUTER_API_KEY` — the seeded default chat model runs on **OpenRouter**, not OpenAI, and no OpenAI model is seeded. Get a key at [openrouter.ai](https://openrouter.ai)
- `GOOGLE_API_KEY` — memory embeddings and vision run on **Google Gemini**. Get a key at [Google AI Studio](https://aistudio.google.com/apikey)
- A WorkOS account (free tier) — see [Authentication](/self-hosting/authentication)
- A [Cloudinary](https://cloudinary.com) account (free tier works) — see [Media storage](#media-storage) below

## Media storage

<Warning>
Chat file uploads, generated images, and profile pictures are stored on [Cloudinary](https://cloudinary.com), not on your own infrastructure. Set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` (see [Environment variables](/configuration/environment-variables)) before relying on these features.

Without them the API still boots — Cloudinary is configured with a warn-and-degrade strategy, not a hard startup requirement — but every upload/image/profile-picture call fails at request time until the keys are set.
</Warning>

Routing media through GAIA's own JuiceFS/S3 workspace storage instead of Cloudinary is a known, unscheduled follow-up (it touches five call sites plus URL-shape parsing in the support-ticket flow) — not something this self-hosting setup half-builds today. A free Cloudinary account is the supported path for now.

  </Step>

  <Step title="Start services">
    ```bash
    gaia start
    ```
  </Step>

  <Step title="Monitor and open GAIA">
    ```bash

    gaia logs
    ```

    - Web: http://localhost:3000
    - Backend API: http://localhost:8000
  </Step>
</Steps>

## Advanced: workspace storage on macOS and Windows

You only need this if you plan to run the backend outside the default Docker setup.

<Note>
Run the backend in a container on every platform. Its workspace storage (file uploads, artifacts, skills) uses JuiceFS, which mounts through Linux FUSE, a native backend on macOS or Windows can't provide it. Docker Desktop covers this on all platforms. See [Docker setup](/self-hosting/docker-setup#persistent-workspace-storage-juicefs-and-fuse) for the FUSE requirements and configuration.
</Note>
